# swa.ml 2.3 release (draft)

**Status: unreleased draft, 18 November 2026.** The 2.3 candidate is allocated (WP1a) as an unreleased candidate; nothing in this file is published. The owner approved releasing swa.ml 2.3 as a compatible minor edition after 2.2 with the scope below. The decisions are [ADR 0022](decisions/0022-values-places-and-expressions.md), [ADR 0023](decisions/0023-state-reactions.md), [ADR 0024](decisions/0024-communication-and-package-links.md) and [ADR 0025](decisions/0025-real-time-placement-and-binding.md). The rules to implement, each tagged with its work package, are in the [2.3 chapter drafts](drafts/2.3/README.md). The design record is the [2.3 proposal](proposals/NEXT_MINOR_PROPOSAL.md), revision 2; the ADRs are normative where they differ.

Allocated identifiers (WP1a): standard 2.3, parser and host semantics 2.3, reference profile `swaml-reference/2.3`, reference implementation package 4.0.0. WP1 has landed: assignment to places (`statuses[i].confirmed = true;`), member access after an index (`recent[i].vehicleId`) and literal component indexes in test inspection paths (`backend.twins[0].link`). WP2 has landed: the whole-expression conditional (`x = if (c) a else b;`, never a statement, only the selected branch evaluated), `view`, `state`, `in` and `out` as contextual words (written unquoted in a 2.3 workspace) and association lists (`associate a, b to 'X', 'Y';`). WP3 has landed: the library packages `Swaml::Numeric` (`minInt`, `maxInt`, `clampInt`, `clamp` and the correctly rounded `sqrt`), `Swaml::Text` (`intText`, `realText`, `boolText`) and `Swaml::Time` (`now()`), in the separate built-in document `libraries/swaml-2.3.swaml`. WP4 has landed: a duration literal is a `uint` value in nanoseconds (`5ms` is 5000000); computed waits `wait (e);`, receive timeouts `or after (e)` and state timers `after (e)`, evaluated when the statement starts waiting or when the entry actions finish, with the catchable runtime failure `DurationRange`; computed periods `on every (e)` and deadlines `deadline (e)` in the constant sublanguage, evaluated per expanded occurrence by one evaluator, `constantValue`; the single-form `PolicySetting`; and the unit warning SW2016. WP5 landed (state reactions: completion transitions, guarded timers, internal transitions, deferral, `CompletionLoop`, SW2017 and SW2018) and was replaced before release by states in the flow (below): none of its forms ships. WP6 has landed: sampled reads `p.m` of required attribute members that declare initial values (`provides attribute ajar: bool = false;`), with sample cells updated at each delivery instant, read live and stable within an activation segment, and the `sample` observation; member policies `connect bodyCan: Cyclic (bcm.bus, dcu.canBus) { crash: CanEvent; }` with the effective policy per member route; and SW2017 for a completion guard that folds to false, with a polling exemption narrowed to reactions that can fire and guards on values that change (WP6-D09). WP7 has landed: release guards `if (g)` on `every`, `receive` and `after` schedule entries (`on every 20ms slot() if (mode.current != PowerMode.sleep) deadline 2ms;`; spelled `when (g)` until package 1 of the states-in-flow specification), bool and pure or reading state in the scope of the entry's arguments, not part of entry identity, evaluated at dispatch before the arguments; a false guard is a `skip` that evaluates no argument and runs nothing, cancels the release's deadline, releases the lock and counts as a completion for `after` successors, a skipped `receive` entry discards its input (`discardInput` reason `releaseGuard`), the periodic grid is unchanged, and a failing guard is a failure of the release with the entry as source (the failing statement when the failure happens in an operation the guard calls) and no successor. WP8 has landed: a deploy path may end at an operation that an effective schedule entry of the addressed occurrence releases (`deploy comMain.storePdu on doorModules[0].core1.isrCan;`), and each entry's effective placement is the most specific one; the library package `Swaml::Os` (`TaskKind`, `Core`, `Task` with `kind`, `priority`, `preemptive`, `periodNs` and `responseNs`) joins the 2.3 library document; on a platform that contains a `Swaml::Os` Task the validator applies T1 to T5 to its Tasks and the entries on them and T6 per Core that has Tasks, also to software on a Node such as an ECU with such Cores below it (only software on a plain Node with no Core with Tasks below it keeps the 2.2 meaning) and, with a Core or a Task, T7 (SW2009); WP8-D11 requires constant Task attributes, WP8-D13 rejects a Task as platform root and the warning SW2021 (WP8-D12) marks an operation placement on a platform without a Task; the in-task position follows deploy order, the deployed tree and schedule order; the reference run orders equal-time releases, dispatches and ready continuations by descending Task priority, Task-placed before unplaced, then in-task position, never preempts (one running activation per Core until it waits or ends), and records `task` on a release on a Task, which Timing uses for its Task lanes; `spec/binding.schema.json` defines `swaml-binding/1`, and `swaml binding check` resolves a binding against the validated model. Package 1 of the [states-in-flow specification](proposals/STATES_IN_FLOW_PROPOSAL.md) has landed: `if` is the one word for conditions, so a release guard is written `if (g)` and an `if` statement's `else` may be followed by another `if` (`else if`). Packages 2a to 5 of that specification are implemented on the branch `v2.3/states-in-flow`: states are steps of the flow, in waiting and periodic machines, and the 2.2 machine syntax and the WP5 forms are removed, with 2.2 machines migrated (section "States in the flow, packages 2a to 5" below). The edition work of WP9 is still open. Every valid 2.2 source without a state machine stays valid with unchanged meaning; a 2.2 source with a state machine is migrated (`node scripts/migrate-machines.mjs`; the user command and the migration guide are package 6 of the states-in-flow specification).

## Compatibility gates

Release gates for D1. WP1a adds them before any language change; every later package and WP9 run them ([ADR 0022](decisions/0022-values-places-and-expressions.md#compatibility)):

1. **Corpus AST identity.** Every repository `.swaml` file, including the showcase models at `examples/showcase/*.swaml`, parses to identical ASTs under the 2.2 and 2.3 grammars, after the single normalization N1 for `PolicySetting`, applied to both sides. The test is `test/v2/compatibility-2-2.test.ts` (unit tests run from `test/v2`).
2. **Behaviour identity.** A fixture recorded once with the 3.1.0 implementation freezes the result of every run in `examples/simulation/runs.json`, every example case and every showcase test (`examples/showcase/*.swaml` on main, run through the API or `--json`): status, full final stores, case verdicts and a SHA-256 digest of the canonical JSON trace (rule WP1a-M02). Every package compares with it, ignoring only `profile` and `languageVersion`. New trace fields and observation kinds appear only where new syntax is used.
3. **Warning-free grammar.** No Langium generation or parser-construction warning, enforced by a unit test.

The gates are in place since WP1a. Gate 1 is `test/v2/compatibility-2-2.test.ts` and gate 3 `test/v2/grammar-warnings.test.ts`, both in `npm test`; gate 3 also fails the build on any `langium generate` diagnostic, hints included (`scripts/langium-generate.mjs`). Gate 2 is `node scripts/compatibility-2-2.mjs runs` in `npm run check`. The fixtures under `test/fixtures/compatibility-2-2/` were recorded with implementation 3.1.0 at `213f583`: the kept 2.2 grammar; `ast.json` (source and normalized AST digests); `behaviour.json` (about 0.8 MB, one line per run or case: options, verdict, status, full stores, machines, deployments, trace length, per-kind counts and trace SHA-256); and, added in the WP1a review from the same commit, `resolution.json` (about 0.7 MB, per corpus file: 2,474 cross-references with their resolved targets, 18 diagnostics with severity, code, range and message, and the inferred types of all 12,640 typed expressions, keyed by offset, length and node type), `projection.json` (about 0.3 MB, per corpus file: the digest of `projectModel`, which the seven views draw from, per kind and top-level owner the count and digest of its projection nodes and edges, the view candidates, and the selection of each of the 86 declared views, filters included) and `behaviour-supplement.json` (the resolved run options of the 131 recorded runs, defaults included, and the four cases of example 32). Example 32 (`examples/32-calibration-bench.swaml`) was added so that gate 2 executes 2.2 constructs no other executed model contained. Its four tests observe: `in` and `out` parameters and routed out arguments with copy-back only after a successful return (an interrupted conversion leaves its target unchanged); `byte` values; a redefined component; a redefined connection whose `Latest` policy keeps only the newer of two queued counts; a redefined operation usage inside a redefined component body; an operation usage nested in an operation body; a multi-binding interrupt; and the second branch of a multi-branch `receive`, taken when a hold arrives first. A removed connection redefinition, hold redefinition or nested usage changes a verdict or a store. Two constructs have no observable behaviour by rule and are covered by gate 1 only: a port redefinition must keep the port type (SW2003), and `returns void` equals an omitted result. Contextual words such as `reversed`, `to`, `by`, `case`, `test`, `use`, `name` and `path` are used as member names, and the view `audit` uses the `not`, `!=` and `path` filter forms (gate 1 records its selection). `node scripts/compatibility-2-2.mjs coverage` lists the parts of the 2.2 grammar (rules, alternatives, optional elements and keywords; presence, not execution) that no executed model contains; after WP1a only `view def` and its documentation remain, which only the built-in library may declare (SW2010) and which gate 1 covers through `libraries/swaml-2.0.swaml`. On a mismatch, gate 2 names every differing key and writes the actual trace under `out/compatibility-2-2/`; `--write-traces <dir>` writes all of them; gate 1 names the differing reference, diagnostic, type, projection group or view. The recorded fixtures are never re-recorded or edited to make a gate pass; `test/ci/compatibility-fixtures.test.mjs` pins the SHA-256 of each of them, checks that each names the recording commit and that this commit is the 3.1.0 implementation of 2.2 (source CI fetches it, and under `CI` a missing commit fails; ancestry is checked only in a full clone). A package that deliberately changes a recorded source (a showcase rewrite in WP9, for example) keeps the recorded bytes at `test/fixtures/compatibility-2-2/sources/<path>`, where both gates read them. Gate 1 fails when a reference of a recorded source resolves to another target, a diagnostic or an expression type changes, or a projection or view selection changes; gate 2 when a resolved run option changes.

**Diagnostic spelling (WP2 review).** Diagnostics on every source, 2.3 sources included, spell names in the 2.2 quoting (`MESSAGE_SPELLING` in `src/language/names.ts`): every name has a 2.2 spelling, and a quoted spelling such as `'state'` is the same name and valid source in every 2.x edition, so a 2.2 source keeps its 2.2 messages byte for byte; the third extended set `models-wp2b.json` (with related information) checks it.

**Consumers of WP2.** A consumer that reads only `Association.occurrence` and `Association.target` sees only the first pair of a list; read every pair with `associationPairs`. Removing an associate statement removes every pair of its list; a tool that deletes one pair rewrites the list (WP2-M04). Every expression walker must descend into `ConditionalExpression` (`condition`, `then`, `otherwise`), which can be the `$container` of any expression. `RESERVED_WORDS` no longer contains `view`, `state`, `in` and `out`, and `isBasicName('state')` is true for 2.3 (`reservedWords('2.2')` and `namesFor('2.2')` give the 2.2 sets). New exports: `ConditionalExpression` and `Association.moreOccurrences`/`moreTargets` (AST); `conditionalType`, `associationPairs`, `associationOccurrences`, `associationTargets`, `isAssociationList` (`semantic`); `reservedWords`, `namesFor`, `quoteName`, `MESSAGE_SPELLING`, `RESERVED_WORDS_2_2`, `CONTEXTUAL_KEYWORDS_2_2` (`names`); `CONDITIONAL_STATEMENT_MESSAGE`, `RECOVERS_STATEMENTS`, `applyStatementRecovery`, `BRACKET_NESTING_LIMIT`, `UNCLOSED_NESTING_LIMIT`, `BRACKET_NESTING_MESSAGE`, `BRACKET_NESTING_CLAUSE`, `PARSER_STACK_MESSAGE`, `guardParserStack` (`swaml-syntax`); `ProjectionEdge.pair`. The name functions treat a non-string edition, such as the index argument of `map`, as the default edition. Every binary chain from `*` up to `or` is written into the `Expression` rule (WP2-G01, WP2-D05): the AST is unchanged, but the CST node of a binary expression of any operator built at the top of an `Expression` now has the grammar rule `Expression` rather than `OrExpression`, `AndExpression`, `EqualityExpression`, `RelationalExpression`, `AdditiveExpression` or `MultiplicativeExpression`. A consumer that recognises an operator by the CST grammar rule name (for example `grammarRule === 'OrExpression'`) must use the AST (`BinaryExpression.operator`) or the token instead. `LangiumParser.parse` no longer throws on a stack overflow; other exceptions propagate unchanged (WP2-D05).

**Consumers of WP3.** A host that evaluates swa.ml provides four new intrinsics with the rules of chapter 1.5: `Swaml::Numeric::sqrt` (IEEE-754, `Arithmetic` below zero), `Swaml::Text::intText`, `Swaml::Text::realText` (exact rounding of the binary value, ties away from zero, no exponent, no negative zero, `Bounds` above 15 decimals or from 1e21; `toFixed` alone is wrong) and `Swaml::Time::now` (the logical time of the evaluating step in nanoseconds, live in every activation). The packages are a second built-in document, `builtin:///swaml-2.3.swaml` from `libraries/swaml-2.3.swaml`; `createSwamlServices` loads both, and a host that assembles its own workspace must load both. Only the built-in declarations are intrinsics (`libraryIntrinsic`), and `isClockRead` identifies `now()` for the effect analysis and for WP4 and WP5. A run's `sources` lists the 2.3 document only when a supplied model imports or references one of its packages, so every 2.2 run keeps its sources. A workspace that declares its own package named `Swaml::Numeric`, `Swaml::Text` or `Swaml::Time` (valid 2.2) uses it: the built-in package of that name is hidden in that workspace, so such a 2.2 source keeps its diagnostics, runs and sources (the fifth extended set). Hiding is workspace-global, as package resolution and duplicate detection are; it is recomputed on every update, a deletion-only update included, and the built-in document's index exports follow it. A shadowing package cannot reach the library operations. Only forms that were invalid in 2.2 change: `import Swaml::Numeric;` (and the other two) was an unknown package and a qualified `Swaml::Numeric::…` name was unresolved; both now resolve when no user package of that name exists. A short call name shared with a 2.3 library operation is SW2001 `Ambiguous name …` with the declarations as related information; nothing that could occur in 2.2 changes its message. A tool that recognises copies of the built-in library must compare against both built-in documents, and lists of loaded documents now contain `builtin:/swaml-2.3.swaml`; a copy of either library document validates with only its duplicate-package errors and hides nothing. A copy may differ only by a leading byte order mark, line ends and whitespace at the end of the file (`isLibraryCopy`, cached per document version); otherwise the bytes must be equal, and a copy with any other change is user source that hides the library packages it declares. Completion of an operation-usage definition (`operation u: …`) now also offers the library operations of visible packages. New exports: `LIBRARY_INTRINSICS`, `LibraryIntrinsic`, `libraryIntrinsic`, `declaredIntrinsic`, `isClockRead`, `isLibraryCopy`, `isLibraryCopyDocument` and `LIBRARY_2_3_URI` (`semantic`); `ambiguousNameMessage` (`swaml-scope`); `hideShadowedLibraryPackages` (`swaml-document-builder`). `guardParserStack` now throws at service creation when the parser library lacks `wrapper.invokeRuleCatch`, and any exception out of a parse leaves the parser state cleared for the next parse.

**Consumers of WP4.** What breaks in a consumer, with the replacement:
- reading `setting.duration`: removed (a TypeScript error); use `settingDuration(setting)`;
- `nanos(entry.period!)` or `entry.period.value`: throws or reads `undefined` on a computed period; use `entryPeriod(entry, occurrence)`, and `entryDeadline(entry, occurrence)` for the deadline, never `entry.deadline ?? entry.period`;
- labels built from `transition.delay`, a receive's `timeout`, `wait.duration` or a setting's `value.duration`: print `undefined` for computed forms; use `displayText(expression)` on `delayValue`, `timeoutValue`, `delay`, `periodValue` or `deadlineValue`, and `settingDuration` for a setting;
- a walker that goes from a policy `Duration` up to its setting: `Duration.$container` is now `Literal | Receive | ScheduleEntry | Transition | Wait` (no longer `PolicySetting`), so the setting is two steps up;
- `PolicySetting.value` is now required (`value: Expression`).

The AST changes are: `PolicySetting.duration` is removed, and every setting has `value: Expression`, a 2.2 duration setting `Literal{duration}` (read it with `settingDuration`); `Literal` gains the optional `duration: Duration`; `Wait.duration` becomes optional and a computed wait has `delay: Expression` instead; `Receive.timeoutValue`, `ScheduleEntry.periodValue`, `ScheduleEntry.deadlineValue` and `Transition.delayValue` are new optional `Expression` properties beside the 2.2 `Duration` properties `timeout`, `period`, `deadline` and `delay`, which stay as they were for literal forms. A consumer that reads `entry.period.value`, `nanos(entry.period)` or `transition.delay` finds `undefined` for a computed form. Periods and deadlines must be read per occurrence with `entryPeriod(entry, occurrence)` and `entryDeadline(entry, occurrence)` (nanoseconds, or `undefined` when not a positive representable duration; the occurrence is the component usage of an expanded occurrence, `Occurrence.structure` of `occurrences`), which call the one evaluator `constantValue(expression, occurrence)` (a bigint or boolean value, or the first `ConstantProblem`); trigger identity is `triggerIdentity(entry)` and `entryKey`: a literal period, or a single literal in parentheses, is its nanoseconds as in 2.2 (so `every 20ms` and `every 20000us` stay one trigger), and any other expression its canonical text `expressionText`; text identity therefore applies only when an expression is computed. Display text for messages and views is `displayText` (`3ms`, not `3000000`). A Timing tool shows a definition's computed period as text (`ProjectionNode.schedule[].periodExpression`, `deadlineExpression`) and an occurrence's evaluated `periodNs` and `deadlineNs`; these fields appear only for computed forms. Every expression walker must descend into the new expression properties, and a tool that recognises a `Literal` by `number`, `text` or `boolean` must accept `duration` (a `uint` value). A host evaluates a computed wait or timeout when the statement starts waiting and a computed state timer when the entry actions finish (expiry at the state-update time plus the value), fails a value that is not positive or not a safe integer number of nanoseconds, and integer overflow of the duration expression's own arithmetic, with `DurationRange`, and records `durationNs` on `wait`/`receiveWait` and the new `timer` observation for computed forms only. `constantNumber` still folds only literals and negation (now also a duration literal) for the 2.2 type and index rules. New exports (`semantic`): `settingDuration`, `displayText`, `expressionText`, `constantValue`, `ConstantProblem`, `ConstantResult`, `representableDuration`, `entryPeriod`, `entryDeadline`, `triggerIdentity`. New diagnostics appear only for new forms; the 2.2 forms keep their 2.2 messages.

**Consumers of WP5.** What breaks in a consumer, with the replacement:
- reading `transition.target` as always present: it is optional; a receive or timer transition without it is internal (`isInternal(t)`), and a completion transition has neither `endpoint` nor a delay (`transitionKind(t)`, `isCompletion(t)` in `semantic`);
- building a Flow edge per transition to `owner.state + '.' + t.target`: an internal transition must not produce an edge (the 3.1.0 projection would have built one to `…undefined`); `projectModel` gives completion edges `completion: true` and the label `when (g)`, a guarded timer edge `guard`, and a state node `reactions` and `deferrals`, all absent on 2.2 sources;
- recognising a transition's trigger by `endpoint ? receive : timer`: a completion transition has no trigger; a timer may also have a `guard`;
- walking a `State`'s members: `State.deferrals` is new (`Deferral.endpoints`, `port.member` strings, `stateDeferrals(s)`); rename and references cover them;
- treating `defer` as an identifier token: it is a keyword token that `Name` accepts (`CONTEXTUAL_KEYWORDS`, `KEYWORDS_FROM_2_3`); it stays a basic name in every edition, so `formatName('defer', '2.2')` is `defer`, and `CONTEXTUAL_KEYWORDS_2_2` excludes it;
- reading traces: a `state` observation may carry `internal: true` (the state is unchanged); `discardTimer` (`state`, `source`, `reason: 'guard'`) and `defer` (`state`, `member`, `source`, `message`) are new kinds; a `violation` with `code: 'CompletionLoop'` names the machine as `subject` and the completion transition as `source` (other violations keep the run target and no `source`); a case it fails has the message `Contract violation CompletionLoop.`;
- printing `transition.target` or `'after ' + transition.delay`: both are `undefined` for internal and completion transitions (`to undefined`, `after undefined`); label by `transitionKind(t)`, `isInternal(t)` and `isCompletion(t)` (or take the projection's labels);
- comparing raw AST JSON with 3.1.0: every `State`, 2.2 ones included, now carries `deferrals: []`;
- new diagnostics SW2017 and SW2018 (warnings) and the SW2008 messages of chapter 4.4, only on the new forms; the SW2000 expected-token lists of parse errors also name `defer` where a state member can start (a parse-error message, as `state` and `view` in WP2).

The AST changes are: `Transition.target` becomes optional, `Transition.guard` may be present on a timer and is the only content of a completion transition, `State.deferrals` and the node `Deferral` are new. Optionality of the generated types against main before WP5: `Transition.target` changes from required to optional; `Transition.guard` stays optional (`guard?: Expression`, declared in the grammar's `interface Transition`, because the completion alternative would otherwise make the inferred type require it); `State.deferrals` is a new array (`[]` by default) and `Deferral.endpoints` a new required array; no other property changes optionality. The declared interface spells `Transition.endpoint`, `Transition.bindings` and `Transition.target` as `string` instead of the aliases `MemberPath` and `Name`, which are `string` too. New exports: `transitionKind`, `isCompletion`, `isInternal`, `isReactionForm`, `stateDeferrals`, `isLiteralTrue`, `attributeAccess`, `AttributeAccess` (`semantic`); `KEYWORDS_FROM_2_3` (`names`); `ProjectionEdge.completion`, `ProjectionEdge.guard`, `ProjectionNode.reactions`, `ProjectionNode.deferrals` (`projection`). A host that executes swa.ml implements the selection order of chapter 6.5 (completion, elapsed armed timers, retained input in global offer-ordinal order, other input in its 2.2 order), `discardTimer`, internal reactions that keep the timer epoch, retention with one `defer` per message, and `CompletionLoop`; a machine without the 2.3 forms runs exactly as in 2.2.

**Consumers of WP6.** What breaks in a consumer, with the replacement:
- treating every dotted value reference `p.m` whose head is not a local or attribute as an error or a field access: when the member `m` of the owned port `p` declares an initial value (`optsIn(member)`, in the definition the port has in that structure after redefinition) it is a sampled read; `sampledReadForm(e, c)` gives the port, the member and the steps after it (`undefined` when a visible local, parameter, loop variable or binding named `p` hides the port, `localVisible(n, name)`), and `sampledReads(c)` and `sampledMembers(c)` the reads and members a component samples (`port.member`) in its executables and in its schedule-entry arguments;
- assuming every required attribute has exactly one owner: a sampled one has zero or one; a tool that lists owners must accept none;
- reading a route's policy from the connection alone (`effectiveQos(connect)`): use `memberQos(connect, member)` for the effective policy of a member route (member policy, else connection policy, else Default) and `memberPolicy(connect, member)` for the declaration;
- assuming `connect` ends with `;`: it may end in a body of member policies (`Connect.memberPolicies`, `MemberPolicy.member`, `MemberPolicy.policy`), which a rewriting tool must keep; a `Documentation` node may sit at the start of the body; in an unfinished source (`{ e: ; }`, `{ : Fast; }`, `{ e }`) `MemberPolicy.member` or the policy reference may be missing although the types declare them: `memberPolicy`, `memberQos`, `projectModel` (which leaves such an entry out of `memberPolicies`) and the simulator tolerate it, and a consumer that reads `mp.policy.ref` must guard it;
- indexing names: `semanticIndex` (rename and references) marks the port, the member and the record fields of a sampled read and the member name of each member policy (a reference to the member of each connected port); a tool with its own index must do the same, or renaming a port or member leaves stale source;
- reading traces: `sample` (`subject` port occurrence and member, `targetPort`, `member`, `value`, `message`, `source`) is a new kind; an unconsumed sampled member has `offer`, `drop` and `discardAge` but no `deliver` or `replaceAttribute`; a stale delivery (a value offered before the value the cell holds, WP6-R02) updates nothing and produces no observation, so an `offer` may have no later observation of its value, and a tool that pairs each `offer` with an outcome must accept one with none.

**Owner decisions in WP6 (provisional; taken in the review fixes, the owner may reverse them).**
- **A. The rule count stays 212.
- **B. A cell never goes back to an older value (review F7).** A value whose offer is older than the offer of the value the cell holds does not update the cell: under a fault delay or unequal latencies a delayed older value arrives after a newer one and is ignored, without a `sample` observation (no existing observation kind fits, and none is added; its `offer` remains in the trace). The cell therefore agrees with the newest offered value an owner consumes, as the owner's pending queue already keeps the newest offer. Copies of one offer (duplicates) each still update the cell.

**Consumers of WP7.** What breaks in a consumer, with the replacement:
- assuming a schedule entry ends with its call, `deadline` or `concurrent`: `ScheduleEntry.guard?: Expression` may sit between the call and `deadline`; a tool that prints or rewrites entries must keep it (the formatter prints `if (g)` there; WP7 spelled it `when (g)`, package 1 of the states-in-flow specification respelled it), and every expression walker must descend into it;
- assuming every released activation ends with `complete` or `failure`: a guarded release can end with the new `skip` observation (`subject` the operation occurrence, `activation`, `source` the entry), which follows the activation's `unlock` and has no `value`; a Timing tool ends the activation's interval at it (`projectOperationTiming` does, and lists `skip` among its markers);
- assuming an `after` release follows a `complete`: its `predecessorActivation` may name a skipped activation, and a successor released after a skip cannot rely on the skipped operation's effects (state it would have prepared is stale); a model must guard the successor too (example 51), and the validator says nothing about a successor that relies on a skipped predecessor;
- Timing and run evidence: end an activation interval at `skip` and never count a skipped activation as executed or as a deadline miss (its deadline was cancelled); attribute a later deadline violation only to an activation that is still open, so a skipped activation released at the same instant with the same deadline is never blamed; a whitelist of outcomes or markers (`complete`, `failure`, `interrupt`, `timeout`) must accept `skip`, or evidence from `projectOperationTiming`, which lists `skip` among its markers, is rejected as a whole; a skipped release still has zero-length `release` and `dispatch` intervals, so a tool that counts `dispatch` intervals as executions must subtract the activations that end with `skip`;
- assuming `discardInput` comes from a state machine or an inactive interrupt: reason `releaseGuard` comes from a skipped `receive` entry and carries `activation` and `message`; its `subject` is the operation occurrence (`Demo.c.take`), as for the `skip` and for a machine's `noEnabledTransition` discard, so two occurrences of one definition are told apart by `subject` alone; `discardInput` and `deliver` carry no member, so a consumer identifies the discarded input by its `message` id together with the entry: the `skip` of the same `activation` names the schedule entry as `source` (its trigger is the port and member), and the `publish` or `send` that emitted the same `message` names the member too;
- assuming a `failure` source is a statement: a release guard whose own expression fails has the schedule entry (`Pkg::C/schedule/N`) as `source`, as a failing argument expression already has in 2.2; a failure inside an operation the guard calls names that operation's failing statement, as for an argument; a case it fails has reason `run-failure` and that source;
- comparing a receive binding with the sampled value of the same member in a guard: both hold the new value, because the cell is updated at delivery before the entry is released, so such a guard cannot detect an edge (keep a receive handler that compares with a stored attribute);
- listing the sampled reads of a component: `sampledReads(c)` and `sampledMembers(c)` now include reads in release guards; a tool with its own list must add them, or a member read only by a guard has no cell and no owner exemption;
- indexing names: `semanticIndex` covers attributes, bindings and sampled ports in a guard through the generic reference walk; a tool with its own index must walk `ScheduleEntry.guard`;
- comparing entries: the guard is not part of `entryKey` or `triggerIdentity`; a specialization's entry with the same trigger and operation replaces the inherited one with its guard, or removes the guard (SW2020 warns, WP7-D04);
- reading SW2020: it covers two warnings, told apart by their fixed leading text: `Release guard if (` (WP7 wrote `Release guard when (`) is a guard that folds to false (WP7-D03), and `Replacing entry ` is a replacing entry that drops an inherited guard (WP7-D04); a tool that keys on the code alone must also match the leading text;
- parse-error messages (SW2000) on an unfinished entry: where the parser lists the tokens it expected after an entry's call, the list may now also name `if` (for a stray token after the call it still reports the expected `;`). Parse errors are not part of the compatibility gates.

The AST change is the new optional property `ScheduleEntry.guard?: Expression`; no property changes optionality, and every 2.2 entry has no guard. New projection field: `ProjectionNode.schedule[].guard` (display text), absent on an entry without a guard. New trace kind `skip`; `discardInput` gains reason `releaseGuard` with `activation` and `message`. A host that executes swa.ml evaluates the guard at the activation's first step, before the arguments (live cells and `now()`; attributes live for a serial entry, from the snapshot for a concurrent one; the arguments and the body then read the same cell values), and on a false guard evaluates no argument, runs nothing, cancels the deadline, releases the lock, records `skip`, discards a receive entry's input and releases `after` successors; a runtime failure in the guard is a failure of the release with the entry as source (the failing statement when the failure happens in an operation the guard calls) and no successor. No 2.2 source has a guard, so every 2.2 source keeps its AST, diagnostics, projection and runs; WP7 adds no extended 2.2 set, because it changes no form that 2.2 parses (the new code runs only for an entry with a guard), and the eight existing sets, which hold schedule entries in every 2.2 shape, stay at 0 differences.

**Owner decisions in WP7 (provisional; the owner may reverse them).**
- **A. Observation order.** `skip` replaces `complete` and follows `unlock`, as `complete` does; a receive entry's `discardInput` directly follows its `skip`.
- **B. The source of a failing guard** (reversed by H): the entry, also for a failure inside a called operation.
- **C. One diagnostic per cause.** A suspending, remote or unresolved call in a guard keeps the call rules' message only; the guard's effect message covers calls that write or communicate. A guard on a `start` or `call` entry is reported once and not typed.
- **D. Inherited guards** are typed in every effective structure, as entry arguments are (a redefined helper that writes is an error at the guard's call, reported in the derived component's validation); an unfinished guard in a document with syntax errors is typed nowhere until its syntax is fixed: the validation of a document with syntax errors reports only those errors, and a structure in another document that inherits the entry skips the guard, so a valid file that specializes it gets no error for the unfinished guard (wording corrected in the review, F6; the behaviour is unchanged).
- **E. The guard is evaluated before the arguments (review F1, replacing the proposal's order).** A release whose guard is false evaluates no argument and runs nothing, so a skipped release never runs an argument helper that writes or communicates, and a guard may protect its own arguments (`use(sum % count) if (count != 0)` never divides by zero). - **F. No 2.2 source has a guard, so the gates cannot change.
- **G. A release guard that folds to false is a warning (review F3; WP7-D03, SW2020).** `if (false)`, or a guard on a const that folds to false, never lets the entry run its operation and makes its deadline meaningless, so it gets `Release guard if ({guard}) of {entry} is always false; the entry never runs {operation}.`, at the guard where the entry is written, as WP6-D10 does for completion guards and with the same exemption: a guard that names a const attribute some specialization or usage redefines (matched by the resolved declaration, not the name) folds per occurrence and is not reported. An always-true guard gets no diagnostic. The rule count becomes 213, and 214 with F.
- **H. The failure source of a guard follows the arguments (review F4, reverses B).** A failure in the guard expression itself names the entry; a failure inside an operation the guard calls names the callee's failing statement, as an argument helper and 2.2 do, so a consumer navigates from every failure at one dispatch step the same way.
- **V1. A part redefinition is a replacement too (verification review V1; WP7-D04, decided by the orchestrator, provisional for the owner).** An entry without a guard in `redefines component c: D { schedule { … } }` that replaces a guarded entry written on the redefined usage `c` (a usage-level guard the effective occurrence would otherwise have) gets the WP7-D04 warning at the replacing entry, in the same message form, naming the redefined usage. The two SW2020 messages start with fixed texts, `Release guard if (` (WP7-D03) and `Replacing entry ` (WP7-D04), so consumers can tell them apart without a second code (review V4).

**Owner decisions in WP8 (provisional; the owner may reverse them).**
- **A. WP8-D01 only on `Swaml::Os` platforms (compatibility).** A deploy path that names an operation no entry releases was the 2.2 error `Unknown software occurrence {path}.`; WP8-D01 would change the message of a 2.2 source (for example `deploy c.helper on n;` beside `operation helper() { }`, model w5 of the ninth set). The D01 message is therefore given only on a platform that contains a `Swaml::Os` Core or Task, which no 2.2 source can declare; elsewhere the 2.2 message stays. This is a conflict between the draft and the compatibility rule; the literal draft fails the ninth set (models w5 and w7).
- **B. A total order across Tasks.** WP8-R01 orders equal-priority activations on the same Task by in-task position and otherwise by insertion ordinal; across Tasks this is not transitive (A on K at position 2, B on L, C on K at position 1). Equal priorities exist only on different Cores (T1), so two Tasks of equal priority are ordered by their declaration rank in the platform (depth-first, indexes ascending), then position, then insertion ordinal.
- **C. T4 on a property, not on state syntax.** An activation may suspend when its operation's own code, its states' entry and exit actions or its transition effects contain a `wait`, a `receive` statement, a request (a dotted call) or a call of an operation that may suspend in the same sense; a machine's transitions are its idle selection and do not count. Nothing else of WP5 is used, so a later respelling of states as steps of a flow only has to keep "the idle selection does not suspend an activation". An `interruptible` region does not suspend by itself (its body may).
- **D. What carries a key.** Releases (`every`, `start`, `after`), deliveries that release a `receive` or `call` entry (the entry's key), the execution steps a dispatch schedules, wait expiries, receive timeouts, request expiries and replies (the requesting activation's key). Deadlines, script starts and other deliveries carry none. The dispatch scan visits activations in key order, so at one instant a higher-priority activation takes a component's lock before a waiting lower-priority one. An activation released later in the same instant than a dispatch (for example by an event published at that instant) does not displace work already dispatched: the run has zero-cost steps and no preemption (WP8-R02). *Amended after the WP8 review (F1, decided by the orchestrator, provisional for the owner):* the first implementation keyed only the events and so let such an activation run between two statements of the running one on the same Core. Now each Core that has Tasks runs one activation at a time, from its dispatch or resumption to its next wait or end, whatever the priorities and `preemptive`; the keys decide which ready activation of the Core is dispatched next. Activations on different Cores, and unplaced ones, still interleave statement by statement at one instant, ordered by the keys, as the 2.2 scheduler interleaves components. The simulation orders by priority but never preempts, because statements cost no time; preemption and response times belong to the target and its binding. Worked example (the review's `preempt.swaml`): `L` on a non-preemptive priority-1 Task publishes `toH.e(1)` and then `toC.e(3)`; `H` on a priority-9 Task, released by the first publish, publishes `toC.e(2)`; `C` on a priority-50 Task logs `log * 10 + v`. On Tasks of one Core `L` ends first, then `C` (priority 50) takes 3, then `H` runs and `C` takes 2: `log == 32`, as on plain Nodes. With `H` and `C` on a second Core the result is `23`. In a run with Tasks an `after` successor is released in its predecessor's completion step, so that a higher-priority successor is dispatched before lower-priority work released earlier at the same instant (in 2.2 the release is a separate event, which on a busy Core would let that work take the freed Core first).
- **E. Message context and ranges.** `{entry}` is written `{entry} of {occurrence}` in WP8-D03, WP8-D05 and WP8-D06, as in WP8-D07, because one occurrence placement may cover several components; WP8-D04's entry form ends `; {entry} is not one.`; `{platform}` is the platform root's path; an implicit Core is `the implicit core of {platform}`. A finding about a Task is reported at the platform reference, an unplaced entry at the root reference, an entry finding at the deploy statement that places it, and T7 at the first statement that reaches a second Core; each message once per range.

- **G. Binding details.** *Amended after the WP8 review (F6, decision 3, provisional for the owner):* the schema id is `swaml-binding/1`, a version of its own, so that renaming the release does not invalidate binding files; a root `$schema` string is accepted for editor association; a root-level finding has the pointer `""` in text and JSON; the schema/checker test compares every property's type and range. Duplicate identities in one list are errors; a forwarding connect is not a route; costs may name any operation of the deployed tree (callees too); a placed operation is one that an entry with an effective placement releases, whether on a Task or a Node; package connections count when one end is the deployed root; a missing cost is reported at `/costs`; a file that is not JSON is a schema error; sources with errors exit 1 without resolving identities.
- **H. T6 per Core (review F2, decided by the orchestrator, provisional for the owner; restates WP8-S04; narrowed by V1 below).** T6 applies to an entry when its occurrence is deployed in a Core that has Tasks (an explicit `Swaml::Os` Core, or the implicit Core of a platform whose Tasks are not all under Cores, which spans the platform outside the explicit Cores), or when its own placement is in such a Core. An occurrence is in the Core of its occurrence placement; without one, in the first Core its operation placements reach; otherwise in the Core of the platform root. Software deployed to a plain Node with no Core with Tasks below it is outside the task rules, so a platform may mix OS Cores with plain Nodes: the door showcase's LIN switch panel (`deploy on switchPanelNode;`) needs no OS task, and example 52 now contains that deployment. The D07 example names a Task of the same Core that accepts the entry under T2 to T5 (never an ISR for an `every` entry, an extended Task for one that may suspend); when the Core has none, the message says so (refined by V3 below).

Package 1 makes `if` the one word for conditions (SIF-G01, [chapter 3.3](spec/03-behavior.md#33-statements-and-scopes)):
- **Release guards are written `if (g)`** in the same position, after the call and before `deadline` and `concurrent`: `on every 20ms slot() if (mode.current != PowerMode.sleep) deadline 2ms;`. Their meaning (WP7) is unchanged. WP7 is unreleased, so `when (g)` on a schedule entry is removed, not kept as an alias: it is the syntax error SW2000 ``Expecting token of type ';' but found `when`. - **`else if`** is new against 2.2, whose `else` takes a block only: `if (a) { … } else if (b) { … } else { … }`. The formatter keeps `else if` on one line, with any block comment between the two words; a line comment there ends the line and `if` starts the next one.

**Consumers of package 1.** What breaks in a consumer, with the replacement:
- printing or rewriting a release guard: write `if (` before the guard (`ScheduleEntry.guard` is unchanged); completion data, snippets and highlighting must offer `if` after an entry's call, never `when`;
- the AST: `If.otherwise` is `Block | ElseIf` (was `Block`). The new node `ElseIf` has `statements: If[]` holding exactly the `if` written after `else`, so a walker that runs `otherwise.statements` as a block (as the validator, the stale-read analysis and the simulator do) needs no change, while a walker that tests `isBlock(otherwise)` or opens a scope only for a `Block` must accept `ElseIf`. An editing tool must never insert statements into an `ElseIf`; to add a statement there, rewrite `else if (b) { … }` as `else { if (b) { … } … }`;
- statement identities: none is new. The `if` of an `else if` is statement 0 of its `ElseIf`, so it has the identity of the `if` in the 2.2 form `else { if … }`: `Pkg::C.f/1/otherwise/0`, its branches `…/otherwise/0/then/0` and a chain `…/otherwise/0/otherwise/0/…` in both spellings. Rewriting one spelling as the other (as an editor or a formatter may) keeps every identity and trace source, and `resolveStatement` returns the `if` of the `else if` in a chained source and the `if` inside the block in a nested one. A consumer that must know the spelling tests the node (`isElseIf(if.otherwise)`), not the path. The `ElseIf` node itself, and the condition of an `else if`, belong to the identity of their statements;
- messages: the SW2020 messages read `Release guard if ({guard}) of {entry} is always false; the entry never runs {operation}.` (fixed leading text `Release guard if (`, was `Release guard when (`) and `Replacing entry {entry} drops the inherited release guard if ({guard}) of {component}, so it runs {operation} whatever the guard says; repeat the guard, or write if (true) to remove it deliberately.` (fixed leading text `Replacing entry ` unchanged); a tool that matched `Release guard when (` must match `Release guard if (`. The SW2000 message for `when` after an entry's call is the one quoted above. No other message changes: after `else`, a token that starts neither a block nor an `if` gives the 2.2 message at the missing `{` with the 2.2 recovery;
- the KerML inventory: the production `ElseIf` is new, and `If`, `ScheduleEntry` and the keywords `if` and `when` changed their texts (`when` no longer lists `ScheduleEntry`).

No 2.2 source has a release guard, and `else if` is a syntax error for the kept 2.2 grammar, so the package only turns invalid sources valid: gates 1 to 3 and the nine extended 2.2 sets have 0 differences, no fixture is re-recorded and `amendments.json` stays empty. *Removed.* The 2.2 machine syntax (`initial S;` and `state S { … }` with `final`, ordered transitions `on receive p.m(x) when (g) to T { … }` and `after D when (g) to T { … }`) and every WP5 form (completion transitions `when (g) to S`, guarded timers, internal transitions without `to`, `defer p.m;`), with `CompletionLoop`, the observations `defer` and `discardTimer`, SW2017 and WP5's SW2018 rule. `when`, `initial` and `final` are no keywords of 2.3 (basic names; still reserved when a 2.2 workspace spells names); `defer` is a basic name in every edition. *Added.*
- **Text** (SIF-G01, SIF-S01 to SIF-S08): `state s { … }` stands in the flow or directly in a parent's braces and holds `on entry`, `on exit`, event lines (`on receive p.m(x) { … }`, `after D { … }`, `after (e) { … }`), statements and, last, inner states. `exit;` and `to S;` are statements that stand only inside a state's braces (directly, in `if`/`else` blocks there or in an event line's block); they are the only bodies that may drop their braces (`after 250ms exit;`, `if (wanted) exit;`). An operation with states is directly owned by a component definition, parameterless and `void`, never called and never nested, has no interrupt region and no plain receive statement, and has exactly one effective entry: `on start` (a waiting machine) or `on every P` with or without a release guard and `deadline` (a periodic machine), never `concurrent`.
- **Waiting machines** (SIF-R01 to SIF-R13, SIF-R18): a state is reached once, runs `on entry` once and looks at its items each time something happens to it: arrival, a message it or a parent names (one per look, in delivery order; unnamed owned input is dropped while it waits), a timer of a level (once per arrival, counted from it; phase 1 before deliveries), a write by another activation or a sample update of a value its statements read (SIF-R07, a `wake`; pending while the machine is busy), and one of its own lines writing a name a statement before that line already read (SIF-R08, one re-look). A look walks the parents first, runs the present lines and every statement, reads values as they are when it runs and ends at the first leave; a message is taken when a line on its member runs, and stays queued for the state reached when the look leaves before that line; leaving runs in text order (the block, `on exit` innermost first, entries outermost first, the target's arrival look), and a leave written on a parent leaves everything inside it; a parent reached is looked at before its first inner state is entered. An `if` test in a state's braces is no scheduling step. A loop without time passing ends at the step limit, whose report names the instant and the activations that ran.
- **Periodic machines** (SIF-R14 to SIF-R17): one persistent activation per occurrence keeps its place, locals, loops and timer starts between releases; every release evaluates the release guard (false: a `skip` carrying the activation) and makes one look at the current state, with at most one message; a look that leaves reaches the next state in the same release with its arrival look; a state reached a second time in one release is held (`held: true`, no arrival look; the release ends there); timers run across releases, skipped ones too, and are looked at at the first release at or after their moment; the deadline is per release; reaching the end of the flow (or `return`) is `periodicEnd`: no state is active and the next release starts the flow again with its locals declared again; a machine that fails ends.
- **Diagnostics**: SIF-D01 to SIF-D03 (SW2008), SIF-D04 (SW2006: the condition of an `if` standing directly in a state of a waiting machine reads `now()`, directly or through a called operation). SW2011 follows a leave into `on exit` and into the `on entry` of the state written next. A file in 2.2 state-machine syntax gets one SW2000 error that names the migration.
- **T4** (WP8, section 9): a waiting machine is placed only on an `extended` Task (ADR 0025's exception for the idle wait of a 2.2 stateful operation is withdrawn); a periodic machine may use a `basic` Task when nothing it runs in a release can suspend.

*Owner decisions* (binding; the specification reflects them). `if` never waits; the state waits and looks at what is inside its braces again each time something happens to it: a message it or a parent names, its or a parent's timer, a value its statements read being written by someone else or updated by a delivery, one of its own lines writing a value an earlier statement of the same look already read, and in a machine released `on every P` each release. A periodic machine that reaches its end: nothing happens, no state is active, the next release starts the flow again from the top. Plain statements in a state run at every look, without a warning. A waiting machine needs an extended task; a periodic one may run on a basic task when nothing it runs in a release can suspend. A look reads every value as it is at the moment it runs. Minimum keywords; no pointless warnings.

**Amendments.** `test/fixtures/compatibility-2-2/amendments.json` is the only fixture file a package may edit, and only in a reviewed PR. An amendment may change the message of one recorded gate-1 diagnostic (severity, code and range stay as recorded), remove one recorded warning (`current: null`) that the cited rule retires, or change one recorded expression type to another known type (never `?` or `unknown`). It names the file, the kind (`diagnostic` or `type`, with the type key), the exact recorded value, the exact new value, the rule that requires the change and a reason. The rule is a `WPn-Kxx` identifier defined in a table of the 2.3 drafts, the maintained chapters or the specification (one index function, `knownRules`, finds them wherever a package moves them and ignores a rule when a cell of any of its rows after the identifier starts with `*Deferred.*` or `*Rejected.*`; a unit test pins the 214 identifiers of the drafts and chapters), or an ADR with a file under `docs/decisions`; a WP1a rule never justifies an amendment. Gate 1 fails on a stale entry (the recorded value is not in the fixture), an unused entry (the new value is not produced, or a removed warning still is), a duplicate, an unknown or WP1a rule, a missing reason, any change of severity, code or range, the removal of an error, and any other kind. A 2.2 source never gains an error or any new diagnostic in 2.3, and this is not amendable: a new diagnostic always fails gate 1. References are never amended: a 2.2 name keeps its target. Behaviour (gate 2) is never amended: no 2.3 rule changes the result or trace of a 2.2 source, and new trace information appears only for new syntax; a deliberately changed source keeps its recorded bytes under `sources/`. The list starts empty. The gate-1 report prints every applied amendment with its file, rule, kind and recorded and current values.

### Parser nesting (WP2-D05)

The parser stops a statement whose bracket nesting exceeds the reference limits of WP2-D05 (SW2013): more than 200 brackets open at once, or more than 32 in a statement that ends with brackets unclosed. 200 lies above every depth the 3.1.0 parser reaches; below it the 2.3 parser must parse every valid 2.2 nesting that 3.1.0 parses. The binary chains are written into `Expression` (WP2-G01) so that a nesting level costs three parser rule calls instead of nine. The deepest nesting a parser reaches depends on the stack and on the state of the JavaScript engine, so it is measured, not computed. The table gives nesting levels through the document builder (the parse inside `DocumentBuilder.update`, as in the language server) on Node.js 26.12.0 with the default stack, in a fresh process and in a process warmed by four parses of the same form at depth 60; "current" is the parser without the bracket limit, which the shipped parser applies on top (above 200 brackets, or 100 levels of the two-bracket forms, it reports SW2013 for the statement). In processes that had parsed other sources first, 3.1.0 reached 155 to 160 parentheses and 130 indexes and calls; `test/v2/nesting-limits.test.ts` parses every form at the highest 3.1.0 depth and compares each form with the kept 2.2 grammar in the same process.

| Form (one level) | 3.1.0 fresh | 3.1.0 warm | Current fresh | Current warm |
| --- | --- | --- | --- | --- |
| `(…)` | 148 | 133 | 228 | 261 |
| `a[…]` | 122 | 104 | 205 | 225 |
| `g(…)` | 126 | 105 | 236 | 230 |
| `[…]` (parses; nested array types do not exist) | 122 | 112 | 174 | 205 |
| `record T1 { n = …; }` | 132 | 117 | 246 | 215 |
| `f(…)` around one record literal | 127 | 113 | 235 | 226 |
| `(…)` around one record literal | 147 | 131 | 229 | 288 |
| `g(a[…])` (two brackets) | 64 | 56 | 117 | 109 |
| `k([…])` (two brackets) | 61 | 55 | 112 | 104 |
| `g2(record S { v = …; })` (two brackets) | 62 | 55 | 113 | 101 |
| `a[g(…)]` (two brackets) | 64 | 57 | 117 | 111 |
| `if (x > 0) { … }` (blocks, no brackets) | 388 | 352 | 373 | 336 |
| `if (…) { … } else { …` (an if in every else block, no brackets; SIF-G01) | 290 | 290 | 303 | 277 |
| `if (…) { … } else …` (an `else if` chain, links; 2.3 only) | – | – | 520 | 479 |

Nesting that the host stack cannot hold within the limits (nested array literals from about 175 levels in a fresh process, 180 unclosed blocks) reports SW2013 for its file instead of throwing; 3.1.0 threw a `RangeError` out of the document build there.

**Compatibility exception X1: block nesting near the stack limit.** Nested blocks (`if`, `while` and the other statements with a block) take the same 41 parser frames per level as in 3.1.0, but their deepest nesting can be about 4 to 5% lower: through the document builder in a fresh process, 362 to 373 against 380 to 388 in two independent measurements, and 336 against 352 when warmed with the same form, while after building the examples first this build reaches 385 to 387 and 3.1.0 367 to 369. All these depths depend on the machine and on the process state. The expression grammar makes fewer rule calls, which changes when the engine compiles the shared parser functions and so the stack each level takes. A valid 2.2 source nested between those depths parses in one version and not in the other; where this build cannot hold it, it reports SW2013 for the file (WP2-D05 (c)), and where 3.1.0 could not, it threw a `RangeError`. No other nesting form is lower than in 3.1.0.

**Package 1 and nested `else` blocks (states in the flow, review F1).** `else if` makes the `else` of an `if` an alternation of a block and an `ElseIf`. Written as a rule of its own, that alternation cost one more rule call per nested `else { if … }` level and lowered the fresh depth of that 2.2 form to about 261 (main before package 1: 327; 3.1.0: 290), so 2.2 sources between those depths became SW2013. The alternation is now written inside `If` without a rule of its own: in a fresh process the form reaches 303 levels, above 3.1.0, and the nested `if` blocks of the row above reach 401 against 389 for 3.1.0 measured the same day. Warmed by the same form it reaches 277 levels against 290 for 3.1.0 (main: 303), which is the block-nesting effect of exception X1 for this form; an `else if` chain takes fewer frames per link and reaches 520 links fresh and 479 warmed. `test/v2/nesting-limits.test.ts` parses and validates both spellings at 270 levels, which the rule of its own did not reach in that process.

## What a door ECU team can and cannot derive after 2.3

After 2.3, the door model fixes a complete, statically checked task and runnable mapping:
- the Tasks of each Core with kind (basic, extended, ISR), priority, preemptability, and period or response bound;
- each runnable's Task and its position in that Task;
- per-entry deadlines consistent with periods and response bounds;
- one Core per component occurrence, no event entries on periodic Tasks, and no suspension on basic Tasks or ISRs (a state machine sits on a basic Task only if none of its reactions can suspend);
- level-triggered mode gating;
- per-member communication policies.

The model carries behaviour and data semantics precise enough for a backend to generate code. It runs deterministically in logical zero time, with equal-time work ordered by Task priority and in-task position. A binding file of costs, budgets and cross-core latencies can be validated against the model and deployment.

It does **not** establish that this schedule meets its deadlines on the target. That needs costs (the binding) plus the Tier 2 timed run or an external analysis. 2.3 does not derive or check:
- response times or schedulability;
- WCET;
- cross-core blocking (excluded by the one-Core rule);
- interrupt latency;
- CAN or LIN signal packing and PDU layout;
- E2E profiles;
- the OS configuration format;
- memory mapping, NvM layout or calibration;
- RTE or generated code.

Passing tests and cases remain bounded evidence of deterministic runs, not proofs.
